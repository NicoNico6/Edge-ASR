# 性能诊断手册：信号 → 原因 → 第一修复

剖析之后用这张表把信号翻译成诊断。结构参考 mit-han-lab/ncu-report-skill 的 diagnosis playbook（MIT），改写为跨硬件通用。具体指标名随硬件和工具版本变化，先用工具枚举可用指标，不照抄别的平台的名字。

| 模式 | 信号 | 原因 | 第一修复 | 例外 |
|---|---|---|---|---|
| 单元闲置 | 并行度（块数、tile 数）少于计算单元数；利用率低 | 工作没有切到足够多的单元上 | 沿未并行的维度切分（split-K、按头或通道）、持久化调度、和相邻算子融合 | batch 1 解码天然并行度小，按 KV 长度切分是常规做法 |
| 尾部效应 | 输入长度方差大；各单元活跃时间差很多倍；时间线末尾长尾 | 少数长任务拖住整体 | 按长度排序或分桶、拆长任务、动态取任务 | 输入长度均匀时不存在 |
| 带宽受限 | 访存吞吐接近峰值、计算单元利用率低 | 每单位计算读的字节太多 | 降位宽、融合减少往返、提高复用（tiling 到片上存储）、改布局让访问连续 | batch 1 解码本来就带宽受限，目标是逼近带宽上限 |
| 计算受限 | 计算单元利用率接近峰值 | 运算量本身大 | 用更低精度的计算单元、减少冗余计算、换算法 | 已接近峰值时收益有限，回到模型侧杠杆 |
| 延迟受限 | 带宽和计算都没用满；停顿集中在等待内存或依赖 | 并发不足以掩盖延迟 | 增加并发（更多在途请求、流水级数、预取）、减少依赖链 | 很小的 kernel 常见，考虑融合 |
| 下发受限 | 主机侧时间长于设备执行；大量很短的 kernel | 每次调用的固定开销占主导 | 融合、批量下发、图捕获（CUDA Graph 等）、整段留在一个单元 | 无 |
| 跨界受限 | 精度转换、拷贝、同步在时间线上占比高 | 切分导致频繁跨单元或跨精度 | 减少跨界次数、合并连续的同类运算到一个单元 | 无 |
| 访存不规则 | 缓存命中低、gather 或非连续访问多、bank 冲突 | 数据布局和访问模式不匹配 | 改布局、预先重排、填充避免冲突 | 稀疏和路由类计算天然不规则 |
| 片上存储溢出 | 寄存器或片上缓冲溢出到 DRAM；占用率低 | tile 太大或中间结果太多 | 缩 tile、分阶段、重算代替保存 | 无 |

用法：一个 kernel 常同时匹配 2 到 4 个模式。按工具给出的预估收益或时间占比排序，先修最大的。每个修复前后用同一个剖析运行目录对比。
