# 懒惰协议

最小改动，偏向删除。研究代码写能复跑的脚本，不建框架。

**为什么：** 多出来的抽象层和配置项会增加阅读负担和出错点。实验代码大多只活几周，框架化的成本收不回来。

**做法：**
- 先问能不能删掉什么来解决问题。
- 只加这次需要的东西，不为想象中的未来需求加参数。
- 简化不改变指标时，保留简化。
- 例外：交付给客户或会长期维护的代码，按产品代码标准写。
