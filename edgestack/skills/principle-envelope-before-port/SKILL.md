# 包络先于移植

移植之前先普查包络：支持哪些算子、形状、对齐、dtype、控制流，同步语义是什么，失败时是报错、静默错算还是退回 CPU。写成带版本号的包络表，再动计算图。

**为什么：** 手册和实际行为经常不一致，模拟器和硬件也经常不一致。包络边缘的失败往往是静默的：结果错了但不报错。逐版试出来的约束如果不记下来，下一个人会再试一遍。

**做法：**
- 用 **opcensus** skill：列出模型的算子、形状、dtype，对照包络表，标出不支持、要改写、要回退的部分。
- 每条约束记发现时的 SDK 或固件版本和最小复现，放进项目的硬件怪癖文件。
- 每条加速路径配 init 自检、运行时门控和回退路径，失败时自动回到参考实现并留日志。
- 模拟器上通过的算子必须在板上再对拍一次。

**边界：** 区别于 **principle-parity-ladder**，那条管怎么逐级对齐数值；这条管动手前先知道哪些路走得通。
